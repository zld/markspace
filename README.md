# MixForge

Deterministic offline and streaming timeline mixing for a game-audio build
pipeline. One project JSON describes tracks, buses, automation, fades and a
loop region; the same mix graph serves both the offline render and the
block-streaming render, and a compare mode proves the two produce identical
samples.

## Setup (macOS, Python 3.11)

From the project root:

```sh
python3.11 -m venv .venv
.venv/bin/python -m pip install numpy==1.26.4 soundfile==0.12.1
.venv/bin/python -m pip install -e .          # console script + src layout
```

All dependencies live in `.venv`; nothing is installed into system Python.

## Demo and acceptance run

```sh
.venv/bin/python scripts/demo.py --workdir .demo
.venv/bin/python -m mixforge.cli render \
  --project .demo/project.json --mode compare --block-size 1024 \
  --output .demo/mix.wav
```

The demo writes three deterministic WAVs (48 kHz mono dialogue, 44.1 kHz
stereo music, 32 kHz mono ambience) and a 48 kHz / 5 s / 3-track project with
linear and step automation, fades, a music bus, a loop region and a limiter.
The WAV fixtures are generated by `scripts/demo.py`; no external files are
referenced.

`python -m mixforge.cli` works from the checkout through the root-level
`mixforge/` import shim, and `mixforge` / `python -m mixforge.cli` work after
the editable install. `.venv/bin/mixforge ...` is equivalent.

## Modes

| Mode | Behavior |
| --- | --- |
| `offline` (default) | Renders the project in bounded chunks and writes a WAV. |
| `stream` | Consumes blocks of `--block-size` and writes WAV incrementally. Never assembles the full mix. |
| `compare` | Streams blocks, lazily renders matching offline chunks, and compares every sample. Writes the WAV only when identical. |

`--summary PATH` additionally writes the JSON payload to a file.

## Output contract

Successful runs print JSON and exit `0`:

```json
{
  "status": "ok",
  "mode": "compare",
  "sample_rate": 48000,
  "channels": 2,
  "frames": 240000,
  "track_count": 3,
  "bus_count": 3,
  "tracks": [
    {"id": "dialogue", "frames": 240000, "samples": 480000, "peak": 1.067,
     "rms": 0.295, "clip_count": 714, "clip_domain": "track_post_gain",
     "source_sample_rate": 48000, "source_frames": 144000,
     "clip_frames": 144000, "start_frame": 12000, "mute": false,
     "bus": "dialogue", "automation_keyframes": 6}
  ],
  "buses": {"music": {"peak": 1.456, "rms": 0.392, "clip_count": 13518,
                       "clip_domain": "bus_post_gain"}},
  "master": {"peak": 1.240, "rms": 0.385, "clip_count": 4866,
             "clip_domain": "master_pre_limit"},
  "master_post_limit": {"peak": 0.98, "rms": 0.382, "clip_count": 0,
                        "clip_domain": "master_post_limit"},
  "automation_samples": [
    {"track": "dialogue", "frame": 1024, "gain_db": -5.488,
     "effective_gain_db": -7.488, "roles": ["block_boundary"]}
  ],
  "block_boundary_stride": 1,
  "max_abs_diff": 0.0,
  "first_diff_sample": null,
  "identical": true,
  "streamed_blocks": 235
}
```

Details:

- `peak`, `rms`, `samples`, `clip_count` are present for every track, every
  bus and the master.
- `clip_count` counts samples with `abs(sample) >= 1.0`.
- `clip_domain` states exactly where clipping was measured:
  `track_post_gain`, `bus_post_gain`, `master_pre_limit` or
  `master_post_limit`. Both master domains are always reported, so limiter
  attenuation is never confused with clipping at a track or bus.
- `automation_samples` lists keyframes, block boundaries and loop boundaries
  (plus their immediate neighbours) with the interpolated gain and its roles.
  Keyframes, loop edges and endpoints are always included; block boundaries
  are strided when needed so the listing stays bounded even for
  `--block-size 1`. `block_boundary_stride` reports the stride, and thinned
  rows carry the role `block_boundary_sampled`.
- `compare` reports `max_abs_diff` and `first_diff_sample` (a flat
  frame-major sample index, or `null` when identical).

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Success; in compare mode, outputs are sample-identical. |
| `2` | Configuration, project validation or WAV/JSON I/O error. Errors carry a `location` such as `tracks[2].automation.points[1].time`. |
| `1` | Offline/stream mismatch, non-finite processing, or unexpected internal failure. |

## Project schema

```json
{
  "sample_rate": 48000,
  "channels": 2,
  "duration_seconds": 5.0,
  "tracks": [
    {
      "id": "dialogue",
      "path": "assets/dialogue.wav",
      "start_seconds": 0.25,
      "gain_db": 0.0,
      "mute": false,
      "bus": "dialogue",
      "fade": {"in_seconds": 0.02, "out_seconds": 0.05},
      "automation": {
        "unit": "seconds",
        "interpolation": "linear",
        "points": [{"time": 0.0, "gain_db": -6.0}, {"time": 1.0, "gain_db": -3.0}]
      }
    }
  ],
  "buses": [{"id": "dialogue", "gain_db": -2.0}],
  "master": {"gain_db": -1.5, "limiter": {"enabled": true, "ceiling": 0.98}},
  "loop": {"start_seconds": 1.0, "end_seconds": 1.5, "count": 3}
}
```

- `duration_frames` may replace `duration_seconds` (exactly one is required).
- Positions accept either `*_frame(s)` integers or `*_seconds` values; declaring
  both for one field is an error. Frame values must be non-negative and no
  larger than `2**53 - 1`; larger values are configuration errors rather than
  NumPy index overflows.
- Automation `unit` is `"seconds"` or `"frames"`; `interpolation` is
  `"linear"` or `"step"`. Keyframes must be unique after conversion, gains
  finite, and positions non-negative. Gains interpolate in the dB domain;
  positions outside the keyframe range hold the endpoint value.
- Fade durations are clip-local source frames and must fit inside the clip.
- `loop` repeats `[start, end)` `count` times starting at `start`; it must lie
  inside the project duration, including all repetitions. Automation is
  evaluated on the output timeline, so repeats never reset keyframes.

## Processing notes

- Resampling is deterministic linear interpolation in NumPy; output length is
  the target duration rounded half away from zero. Empty input, a single
  source frame, and a zero-frame target are explicit cases.
- Each block is rendered from absolute timeline positions, so block size
  affects neither automation, alignment, nor samples.
- Mono sources are duplicated to stereo; stereo sources are averaged for a
  mono project.
- NaN/Inf in source WAVs, resampling output, mix output or statistics raises a
  located `ProcessingError`; nothing is silently zeroed.
- Read failures name the track and block range (`track[id].path` plus
  `block_start` / `block_frames` in the error context).

## Tests

```sh
.venv/bin/python -m pytest -q
```

- `tests/test_render.py` — resampling, automation, fades, statistics domains,
  offline block-size invariance and graph-vs-resampler correctness.
- `tests/test_stream.py` — offline/stream equality across block sizes, short
  final blocks, zero-frame projects, loop semantics, mono/stereo handling,
  laziness, and mid-stream read failures with track/block context.
- `tests/test_edges.py` — CLI exit codes, locatable validation errors,
  malformed JSON, NaN WAVs, mismatch reporting (max diff and first diff
  sample) and `inspect`.

## Layout

```
src/mixforge/
  cli.py         argument parsing, JSON summaries, exit codes
  model.py       project/track/bus/automation validation
  schema.py      shared JSON primitive validation
  automation.py  keyframe interpolation, fades, automation sampling
  resample.py    deterministic linear sample-rate conversion
  graph.py       tracks -> buses -> master mix graph
  render.py      offline renderer
  stream.py      block streaming renderer
  stats.py       peak/RMS/clip statistics and sample comparison
  io.py          WAV/JSON readers, incremental WAV writer, seekable sources
scripts/demo.py  deterministic sample project generator
```
